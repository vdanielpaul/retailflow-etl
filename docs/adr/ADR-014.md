# ADR-014: Medallion Dataset Architecture

## Status
Approved

## Context
RetailFlow ETL requires processing raw POS CSV transactional data into structured, clean, and normalized Star Schema models. Combining ingestion, validation, cleaning, and reporting inside a single database zone makes auditability difficult, leads to high schema drift risk, and prevents re-running processing on raw historical data.

We need a clear pipeline flow to organize staging, schema validation, and warehouse storage.

## Decision
We implement a three-tiered **Medallion Architecture** inside BigQuery:
1. **Bronze Layer (`retailflow_bronze`)**: Holds raw, append-only staging data loaded directly from GCS files. Raw rows are kept as JSON string payloads with ingestion metadata (timestamps, filenames) and expire after 30 days.
2. **Silver Layer (`retailflow_silver`)**: Holds cleaned, validated, and schema-enforced Canonical Data Model (CDM) records (retained indefinitely).
3. **Gold Layer (`retailflow_gold`)**: Holds the final dimensional warehouse Star Schema (facts and dimensions) with resolved surrogate keys (retained indefinitely).
4. **Metadata Layer (`retailflow_metadata`)**: Dedicated audit zone tracking run execution watermarks.

## Consequences
- Clean separation of concerns: Ingest vs Validation vs Reporting.
- Audit trail: Bronze retains the raw input exactly as it arrived for 30 days, enabling reprocessing or historical comparisons during issues.
- Optimized cost: 30-day auto-expiration on the Bronze staging tables keeps raw storage costs low.

## Alternatives Considered
- **Single-stage Database Ingestion**: Rejected because it prevents raw data auditing and increases risk of loading unclean records into reporting tables.
- **Dataflow Direct to Gold Ingestion**: Rejected because it requires executing complex, memory-heavy dimension table joins inside Dataflow worker nodes.
