# ADR-016: Event-Driven File Ingestion Trigger

## Status
Approved

## Context
RetailFlow ETL v2.0 requires an event-driven system to detect POS CSV raw files immediately upon landing in GCS. Standard file-polling mechanisms require scheduled batch runs, introducing latency and operational CPU costs. 

We need a low-cost, serverless integration to notify downstream services as soon as a new GCS object is finalized.

## Decision
We implement a GCS-to-Pub/Sub trigger pipeline using native GCP integrations:
1. **Google Storage Notification**: Configure `google_storage_notification` to bind the GCS raw bucket upload events (`OBJECT_FINALIZE`) to publish message notifications to a dedicated Pub/Sub topic (`retailflow-ingest-trigger-topic`).
2. **System IAM Authorization**: Retrieve the system-managed GCS service account using `google_storage_project_service_account` and assign it `roles/pubsub.publisher` on the target topic to allow publishing messages.
3. **Implicit Dependency Constraints**: Enforce that the Storage Notification depends on the IAM binding using `depends_on = [google_pubsub_topic_iam_member.gcs_publisher]`.

## Consequences
- Immediate event detection: Downstream triggers run only when new files arrive, achieving true serverless utility billing.
- Decoupled storage and compute: Storage triggers decouple GCS writes from the execution of the Cloud Function and Dataflow pipeline.
- Reliable delivery: Pub/Sub buffers message logs for up to 7 days if downstream services are temporarily unavailable.

## Alternatives Considered
- **Direct Cloud Function Storage Triggers**: Rejected because it directly binds GCS to the Cloud Function, preventing message queuing, buffering, or multiple parallel subscribers.
- **Poll-Based Scheduler Ingestion**: Rejected because polling GCS buckets adds execution complexity, API charges, and latency.
