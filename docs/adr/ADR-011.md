# ADR-011: BigQuery Adoption

## Status
Approved

## Context
RetailFlow ETL v1.0 used PostgreSQL as its target data warehouse. For an enterprise cloud modernization scaling to 2,500+ stores and handling large historical POS data query sets, managing a transactional database (PostgreSQL) introduces limits on analytical scalability, write locks during bulk operations, and high operational management overhead.

We need a scalable, serverless target data store that accommodates column-store analytical queries, bulk write performance, and zero server maintenance.

## Decision
We select **Google BigQuery** as the primary data warehouse backend. 
- All data tables are migrated from PostgreSQL schemas to BigQuery datasets.
- We utilize BigQuery Load Jobs for bulk data ingestion.
- Analytical transformations (Silver to Gold mapping and surrogate key joins) will execute using BigQuery SQL MERGE statements.

## Consequences
- Serverless scalability: BigQuery scales from megabytes to petabytes automatically with no virtual machine provisioning.
- Lower ingestion cost: BigQuery Load Jobs are free of charge.
- High performance column-store query speeds for warehouse reports.
- Separation of operational compute (Dataflow) from storage (BigQuery).

## Alternatives Considered
- **Cloud SQL for PostgreSQL**: Rejected because managed transactional databases still suffer from table locking and scale limitations for massive analytical workloads.
- **Google Cloud Spanner**: Rejected because Spanner is optimized for high-concurrency transactional OLTP workloads, whereas our use case is purely read-heavy OLAP analytical reporting.
