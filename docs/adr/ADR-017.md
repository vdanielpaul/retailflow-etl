# ADR-017: Metadata Repository Pattern

## Status
Approved

## Context
RetailFlow ETL v2.0 requires querying watermarks and logging execution metrics. Spreading raw SQL string parameters or Google Cloud BigQuery API clients directly inside the ingestion coordinator services binds the application layer tightly to the database infrastructure. 

If we choose to migrate from BigQuery to another analytical warehouse (e.g. Snowflake or local Postgres), we would have to modify the core application service, risking business logic regression.

We need a persistence boundary that isolates BigQuery-specific details from the ingestion application service.

## Decision
We implement the **Repository Pattern** to decouple data storage from the application layer:
1. **Interface Contract**: Define a `WatermarkRepository` abstract base class outlining domain data methods: `exists(file_hash)`, `create_watermark(record)`, and `record_audit(record)`.
2. **Infrastructure Implementation**: Implement `BigQueryWatermarkRepository` executing BigQuery SQL queries. It handles query formatting, parameters binding, and translates BigQuery API exceptions into domain-level exceptions.
3. **Centralized Client Management**: The repository constructor receives the `google.cloud.bigquery.Client` dependency via constructor injection. The lifetime of the client is managed globally by the dependency injection container.
4. **SQL Isolation**: All parameterized SQL queries are stored in a dedicated module (`repositories/sql/queries.py`) instead of inline strings.

## Consequences
- Clean separation of concerns: The application layer is database-agnostic.
- Testability: We can mock the repository interface in unit tests without mocking the BigQuery client.
- Zero database-specific exceptions leaked: Database API errors are translated into `WatermarkLookupError` or `MetadataPersistenceError`.

## Alternatives Considered
- **Active Record / ORM (SQLAlchemy)**: Rejected due to BigQuery's analytical nature; ORMs add substantial runtime latency and overhead compared to raw SQL queries.
- **Inline SQL Queries**: Rejected because it mixes infrastructure-specific logic with ingestion application service coordination.
