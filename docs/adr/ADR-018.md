# ADR-018 — Decoupling Business Validation from Pipeline Context

**Status:** Accepted
**Date:** 2026-07-25
**Author:** Data Engineering Team
**Supersedes:** N/A
**Related:** ADR-017 (Adapter Pattern for Beam Integration)

---

## Context

### Original Design

When RetailFlow ETL v1.0 was designed, all pipeline components shared a `PipelineContext` object. This context carried:

- `source_file` — the path of the CSV being processed
- `run_id` — the unique pipeline execution identifier
- `metrics` — a shared metrics accumulator
- `config` — pipeline-wide configuration settings

The `BaseValidator` abstract interface required a `PipelineContext` argument on all `validate()` calls:

```python
@abstractmethod
def validate(self, df: pd.DataFrame, context: PipelineContext) -> ValidationResult:
    ...
```

This made sense in v1.0 because:
- All validators ran within a single process
- `PipelineContext` was constructed once at pipeline start
- Passing it through was natural — it was always available

### The Modernization Problem

During Task 3.3 (validation engine integration into Apache Beam), it became necessary to invoke the `BusinessRuleValidator` from a framework-agnostic adapter layer. The adapter must:

1. Accept a single canonical record dict (the Beam element representation)
2. Invoke the validator
3. Return a structured result

Constructing a `PipelineContext` stub inside the adapter was the initial approach. This would have required:

```python
# Proposed compatibility stub — rejected
context = PipelineContext(
    run_id=run_id,
    source_file=filename,
    config=None,  # stub
    metrics=NoOpMetrics(),  # stub
)
result = validator.validate(df, context=context)
```

A permanent compatibility shim introduces complexity, future maintenance risk, and misrepresents the dependency relationship.

---

## Investigation Findings

A systematic review of all five validators was conducted to determine which actually accessed `PipelineContext` fields:

| Validator | Context Fields Accessed | Verdict |
|---|---|---|
| `FileValidator` | `context.source_file` | Used — for file-level reporting |
| `SchemaValidator` | None | Interface-only dependency |
| `DataTypeValidator` | None | Interface-only dependency |
| `BusinessRuleValidator` | None | Interface-only dependency |
| `DuplicateValidator` | None | Interface-only dependency |

**Finding:** Four of five validators accepted `PipelineContext` only to satisfy the abstract interface contract. They never read from it. The dependency was an artefact of the original interface design, not a real functional requirement.

---

## Decision

Make `context` optional on the `BaseValidator` interface and all concrete implementations:

```python
# Before
@abstractmethod
def validate(self, df: pd.DataFrame, context: PipelineContext) -> ValidationResult:
    ...

# After
@abstractmethod
def validate(
    self,
    df: pd.DataFrame,
    context: Optional[PipelineContext] = None,
) -> ValidationResult:
    ...
```

`FileValidator` was updated to guard the access:

```python
source_file = context.source_file if context is not None else None
```

All other validators required only the signature change — no logic changes.

---

## Consequences

### Positive

**Portability.** Validators can now be invoked from any Python context without constructing a pipeline context object. This makes them usable in:
- Beam adapters (current use case)
- Unit tests (no mock context required)
- Future Spark or Flink adapters
- CLI data quality tools
- Ad-hoc data investigations

**Simpler adapters.** `BusinessRuleAdapter` invokes `validator.validate(df)` directly. No stub construction, no mock objects, no compatibility layer.

**Accurate dependency modeling.** The interface now reflects the real dependency. `FileValidator` uses `context` — its signature communicates this truthfully. The other four validators do not.

**Reduced test complexity.** All validator unit tests can be written without constructing `PipelineContext` instances.

### Neutral

**`FileValidator` behavior unchanged.** The validator guards the field access and falls back to `None` when context is absent. The existing v1.0 call sites continue to pass context explicitly and are unaffected.

### Negative / Risks

**Interface permissiveness.** Making `context` optional means the interface no longer enforces that callers provide execution context. A future validator that genuinely requires context would need to raise an explicit error if called without it — this is now the validator's responsibility rather than the interface's.

**Mitigation:** Document this clearly in `BaseValidator`'s docstring. Any new validator that requires context should validate its presence explicitly in `validate()` and raise `ValueError` with a clear message.

---

## Alternatives Considered

### 1. Permanent Compatibility Stub

Construct a minimal `PipelineContext` inside the adapter with stub objects for unused fields.

**Rejected.** A stub carries permanent maintenance risk. If `PipelineContext` gains new required fields, the stub breaks silently. It also obscures the actual dependency relationship.

### 2. Introduce a Separate Validator Interface for Beam

Create a `BeamValidator` abstract class with a different signature, duplicating the validator hierarchy.

**Rejected.** This creates two independent implementations of the same business rules, which is the root problem the modernization strategy is designed to avoid.

### 3. Remove PipelineContext from the Interface Entirely

Make validators fully stateless by removing the context parameter entirely and having callers resolve `source_file` before calling.

**Considered but deferred.** This is a more complete refactoring that would require updating all v1.0 call sites. The current approach achieves the immediate goal with minimal change. A full removal can be evaluated during a future cleanup sprint.

---

## Production Considerations

At Dataflow scale, validators are instantiated once per worker bundle in `setup()`. The context parameter, when provided, carries pipeline-run metadata. If `PipelineContext` is extended in the future (e.g., to carry distributed tracing context or GCP project configuration), the optional parameter provides a clean extension point without breaking the adapter interface.

## Interview Talking Points

- "We discovered that four of five validators had a dependency they didn't actually use — a common form of interface coupling."
- "Making the context optional was a minimal, safe change with significant portability benefits."
- "It's an example of reducing coupling by discovering the true dependency boundary rather than adding compatibility layers."
- "The adapter pattern made this discovery inevitable — when you try to use a component in a new context, latent dependencies surface."
